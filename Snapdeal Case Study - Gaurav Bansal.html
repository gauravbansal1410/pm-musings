06The real finding

They receive the order, and only now decide to pay. COD doesn’t move the purchase decision earlier, it delays the actual commitment to this moment, after every step above has already eroded it. Checkout was never the sale. This is.

(Post-order journey, repeat behavior, continues from here, out of scope for this assignment)

Market context Not a Snapdeal-specific pattern but across Tier 2/3 D2C brands, COD orders return at 28–35% vs 4–8% for prepaid (Pragma, 2024 analysis of 142 brands), the same commitment gap, market-wide.

3Diagnosis

What I tested, and how it compares to Meesho

Verified by placing and cancelling real orders on both apps, not by reading marketing copy

What Snapdeal already gets right — verified by direct testing

Incomplete addresses get blocked

House number and street are mandatory, the order can’t proceed without them. Closes off one failure category before it starts.

Prepaid is the actual default

Pay Online carries a live discount and is pre-selected. COD is the alternative you have to actively choose.

The WhatsApp promise doesn’t hold

App states updates come via WhatsApp by default. We placed and cancelled a real order, no message arrived at any stage.

Vs Meesho — verified differences

Payment default is reversed

Meesho pre-checks COD by default, shown below. Snapdeal already defaults to Prepaid, shown above, this is one place Snapdeal’s design is already ahead.

Cancellation framing differs

Snapdeal leads with loss aversion and six fixed reasons, no free text. Meesho uses neutral framing, a localized trust banner, and an open text field Snapdeal doesn’t have.

8Execution

Trust design approach (asked specifically in the assignment)

My understanding of the question

Not to list another set of levers but to make sure those already presented in this solution set pass this test. This is the test that decides whether a new lever earns trust, or just borrows it.

The principle

Trust doesn’t break at the moment of asking the customer for something, money upfront, a GPS permission, a verification step. It breaks at the gap between what’s promised and what’s actually true once they’ve acted on it. Asking isn’t the violation. An unhonored promise is.

Customer-facing version of a case constraint → “No dark patterns”

The test every lever has to pass

For every promise this plan makes to the customer, explicit or implied, does it hold up once they’ve acted on it?

Not hypothetical: My own testing for this study already found one broken promise, WhatsApp updates claimed by default, no updates arrived. That gap is exactly what this principle has to close.

Geo-pin discount Passes clean

Location-for-discount is instant and self-contained, nothing promised about the future that could later go unkept

WhatsApp connect Passes the ask, not yet the promise

₹10 off is instant but not yet realized. But verifying WhatsApp implicitly promises updates will now actually arrive. It holds true if the send-pipeline itself gets fixed alongside the verification gate. Ship the gate without fixing the pipeline, and this becomes the same broken promise.

Token / partial pay Conditional

Only passes if the ₹30 forfeiture-on-doorstep-refusal rule is stated before the customer commits the money. Undisclosed, the ₹30 becomes exactly the kind of promise this principle exists to catch.

9Execution

Customer Trust Score (asked specifically in the assignment)

Bonus — not part of the 90-day plan

Forward-looking, deliberately. Not for the current plan. The FTU cohort in this plan can’t generate the data this needs yet.

Inputs

Delivery acceptance rate, Returns requested, Fraud attempts flagged, COD reliability, address stability, prepaid share over time

Tiers

New (no history) → Building (1–3 orders) → Trusted (4+ clean orders)

Action

Shifts incentive intensity only. Never blocks access, “no blanket COD blocking” is a case constraint. Frictionless COD for Trusted, nudged toward prepaid for repeat low-trust refusers.

The gap: this cohort is entirely FTU. The first scorable fact, a first order resolving into a kept delivery, doesn’t exist until exactly where the journey map ends. The Cut decision holds, individual history isn’t there yet.

If a score is wanted before that history exists — proxy signals for FTU (need reliability correlations)

Geographic

  • Geo-pin clusters (once adoption builds), finer than pincode, immune to address-text ambiguity
  • Aggregate locality reliability, same data already powering Pincode Social Proof, pointed inward

Address type

  • Residential vs commercial keyword detection: Shop No., Factory, Godown vs Flat, House No., Society
  • Two of five personas run commercial addresses, Rajesh and Suresh

Intent & account

  • Returning non-converter, browsed before without ordering, Rajesh’s exact pattern
  • Referral source inherits some of the referrer’s trust
  • Phone / WhatsApp verification status

Worked example: Rajesh browsed twice before this order (intent signal) and runs a registered shop address (commercial signal). Even with zero order history, he’d start at Building, not New.

Proxy-scored customers start more conservative than history-scored customers at the same apparent tier, the signal is noisier. This also sits in tension with the Trust Design principle on the previous slide, proxy scoring is invisible to the customer by nature, a real cost, not a solved problem.
